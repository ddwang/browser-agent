## Prompt caching

By default, when Anthropic models are used, Magnitude will automatically utilize Anthropic's [prompt caching feature](https://www.anthropic.com/news/prompt-caching) to save on token costs as much as possible.

By using prompt caching - Magnitude will use typically around 40% less tokens compared to uncached. The effects of prompt caching compound with longer tasks.

## Configuring prompt caching

If you would for whatever reason like to explicitly disable prompt caching, you can do so:
```ts
const cachedAgent = await startBrowserAgent({
	url: 'https://magnitasks.com',
	llm: {
		provider: 'claude-code',
		options: {
			model: 'claude-sonnet-4-20250514',
			promptCaching: false
		}
	}
});
```
Otherwise, prompt caching will be enabled by default with `anthropic` or `claude-code` providers.

<Warning>Note that prompt caching is not available on Bedrock.</Warning>

## Configuring retained screenshots

By default, Magnitude retains 2 screenshots plus any screenshots still included in a previous cache write. The browser evaluation runner uses 3.

If your task requires complicated interactions and you want to ensure the agent retains more screenshots in working memory, you can increase the `minScreenshots` option:
```ts
const cachedAgent = await startBrowserAgent({
	url: 'https://magnitasks.com',
	llm: {
		provider: 'claude-code',
		options: {
			model: 'claude-sonnet-4-20250514'
		}
	},
	minScreenshots: 3,
});
```


## How Magnitude's memory works

Anthropic provides 4 cache control messages at a time. The Magnitude agent will use one cache control on the system prompt so that it is always cached, and then cycle the other 3 with prompt cache writes and reads to optimize on screenshot tokens during the task.

Magnitude keeps the configured number of recent screenshots, any still-cached screenshots, and the last 20 thoughts in the actor's context. The full observation history remains available in saved memory; filtering does not delete it.

### Current-state observations

Connector observations can opt into `current: true` in their retention options. This renders only the latest observation of that type after cached history, without a cache marker. It overrides `limit` and `dedupe`; use the same retention policy for every observation of a type. Ordinary retained observations keep their existing cache-preserving behavior.

Click feedback uses this mode so frozen history cannot retain superseded click records. A new operation's `lastClick: null` replaces the prior operation's feedback even when memory is reused. Saved memory and `render({ history: 'full' })` still include every snapshot with its original observation number. Current-state rendering does not clear the audit or change notebook provenance.

## Durable task notes

Every planner response must include a `memory_updates` array reviewing the current observations. The host saves these updates before executing the response's actions. An empty array is valid when there are no new facts needed later, including an immediately finishable task. Each update reuses the notebook's stable key, text, and supporting observation numbers. Browser screenshots include the captured URL, which the host attaches to cited notes. These references link a model-written summary to its source; they do not prove that the summary is correct or complete.

Notes survive screenshot and thought eviction. Each update includes `operation` and `expected_text` as well as `key`, `text`, and `sources`:

- `add` requires a new key and `expected_text: null`. An existing key is rejected, never overwritten.
- `correct` requires an existing key and its exact current text in `expected_text`. A missing key or stale text match is rejected. Only that key changes; omitted keys stay unchanged.

Use a separate key for each record or independently correctable fact. A correction must preserve the targeted record's still-valid facts. The host checks key and text matching, not whether the replacement is true or whether it accidentally omits facts within that record. `memory:forget` still removes an explicitly named obsolete note. The actor sees the latest notebook, while saved memory retains the complete note-action audit. Notes are labeled as model-written data, not independent evidence or instructions from a page.

The notebook allows 32 entries, 2,000 characters per note, and 64 KiB of total UTF-8 serialized note data, including source metadata. An invalid reference or capacity overflow returns an explicit error and leaves existing notes unchanged. The agent must correct, consolidate, or forget notes before retrying; nothing is silently evicted.

Each attempted update executes as one audited `memory:note` action and consumes the normal action budget, including rejected writes. Empty reviews consume no actions. A rejected update stops the batch before any remaining updates or browser actions; the next plan sees the error. Earlier successful writes remain saved. Notes do not operate the browser, capture another screenshot, bypass a rate limit, or reset loop detection.

Required reviews work with custom action lists and all actor providers. The planner uses `memory_updates` for writing and `memory:forget` for removing notes. Explicit `agent.exec()` callers use the same guarded `memory:note` schema and receive the action result. `memory.remember(note)` now adds only; `memory.remember(note, currentText)` explicitly corrects a matching record. This changes write semantics and the planner/action contract, not the saved-checkpoint format, and does not add a separate model call. Existing checkpoints with unique keys remain supported; duplicate checkpoint keys are rejected without replacing the current memory.

Each `act()` call starts a fresh notebook unless you explicitly supply an existing `AgentMemory`. Steps within one `act([...])` call share it. `toJSON()` saves notes, and `loadJSON()` restores their source links from saved observations. Legacy checkpoints without notes remain supported.

## Checkpoint instructions and runtime settings

The following restoration fixes are in the current source and are not included in `@ddwang/magnitude-core@0.3.1-ddwang.6`.

`loadJSON()` restores instructions, observations, and notes together, after validation succeeds. Missing instructions clear a previous value; an explicit empty string round-trips unchanged. Invalid instructions or notebook provenance leave the existing memory unchanged. Load only checkpoints trusted for the current user and workflow.

Prompt caching and thought-retention limits are runtime settings, not serialized data. `loadJSON()` preserves the receiving memory instance's runtime settings. When you pass memory to `act()`, the agent applies its current model-specific caching policy; changing that policy clears stale cache markers without deleting observations or notes.

For reused or restored memory, current agent and call prompts replace saved instructions when either is supplied. They are combined once for the call, not appended to prior prompts. If both are omitted, the saved instructions remain. An explicit empty call prompt clears the saved instructions when there is no configured agent prompt. The effective instructions persist in subsequent checkpoints and queries. This is instruction replacement, not conflict detection or a permissions boundary.

For `.6`, construct `AgentMemory` with `instructions: saved.instructions` and the appropriate `promptCaching` value before calling `loadJSON()`. That release ignores current agent/call prompts when memory is supplied. See the [agent integration guide](https://github.com/ddwang/browser-agent/blob/main/AGENT_INTEGRATION.md#checkpoint-restoration) for the version-specific recipe.

Queries use retained history by default and do not receive planner-only notebook commands. Use `agent.query(prompt, schema, { history: 'full' })` to inspect every observation, including repeated screenshots and superseded notebook writes. This audit view does not change the actor's retention, source visibility, or cache state. The eval runner uses it for judging.

The judge loads checkpoint observations and notes without adopting the actor's saved instructions. It receives those instructions as labeled historical data, not system instructions or grading criteria. This separates instruction roles; it does not establish that a model is immune to prompt injection.

`Image` owns a cloned Sharp pipeline configuration and caches the first successful encoding. Rendering, hashing, and checkpointing share that encoding, including concurrent requests. `resize()` returns an independent image. Keep caller-owned source buffers and files unchanged for the image's lifetime; Sharp reads those inputs lazily.
