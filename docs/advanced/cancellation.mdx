---
title: 'Cancellation and deadlines'
description: 'Bound operations without allowing late responses to start new actions.'
---

Magnitude accepts a per-operation `AbortSignal` and an absolute `deadline` (Unix time in milliseconds). Neither option has a default limit. A deadline applies to the entire call, including all steps in `act([...])`, model requests, retries, pauses, and cooldowns.

```typescript
const controller = new AbortController();
const result = agent.act('Complete the requested workflow', {
  signal: controller.signal,
  deadline: Date.now() + 60_000,
});

// On request cancellation:
controller.abort('Request disconnected');

try {
  await result;
} catch (error) {
  // Translate the typed error into your application's tool outcome.
  // A cancelled submission may already have reached the site.
}
```

## Supported operations

| Method | Operation options |
| --- | --- |
| `act(taskOrSteps, options)` | Alongside `prompt`, `data`, and `memory` |
| `query(query, schema, options)` | Alongside memory-rendering options such as `history` |
| `extract(instructions, schema, options)` | Third argument |
| `nav(url, options)` | Second argument |
| `exec(action, memory, options)` | Third argument; pass `undefined` for no memory |

Existing calls without these options remain valid. `maxActions` and browser recovery settings remain agent-level configuration; cancellation does not replace those limits.

## Cancellation versus idle

Cancellation rejects the public call promptly and prevents subsequent Magnitude action dispatch. Model requests receive the cancellation signal; built-in waits stop. Late model output is discarded without saving thoughts or notes.

An already-dispatched browser command or custom action might still be running. During that time, `agent.busy` remains `true`, and another operation rejects with `AgentBusyError`. `agent.whenIdle()` resolves only after the tracked work settles; it does not rethrow the operation's error.

Keep the session out of your reuse pool until `whenIdle()` resolves. Await it in your session scheduler, not in a request handler that must return at its deadline. If custom work never settles, the agent stays busy; retire that session instead of forcing reuse. The lock is per agent, not a cross-process or shared-browser lock.

Only one operation can run on an agent at a time. Nested calls to `act`, `query`, `extract`, `nav`, or `exec` from a custom action also reject as busy. Use the action's connector or underlying API for its implementation.

`stop()` cancels the current operation and closes the browser context. Per-operation cancellation leaves the context open. `stop()` does not wait indefinitely for uncooperative custom work, and it does not make that work safe to reuse.

### Lifecycle coordination

`start()` and `stop()` are serialized in call order. Repeated calls for the same pending transition share its work. Starting an already-ready agent or stopping an already-stopped agent does not rerun connector hooks. If startup fails, Magnitude attempts connector cleanup before rejecting; a later `start()` can retry.

`agent.busy` includes startup, shutdown, queued lifecycle transitions, and draining operations. `whenIdle()` waits for all of that tracked work. `agent.lifecycle` is `new`, `starting`, `ready`, `stopping`, or `stopped`. Lifecycle hooks must not await another lifecycle call on the same agent.

A `start()` during shutdown waits for cleanup. If an operation is still draining, `start()` rejects with `AgentBusyError`. Wait for idle before restarting. Neither `stop()` nor `whenIdle()` proves that a remote submission failed or succeeded. Connector cleanup errors are logged, as before; applications remain responsible for retiring sessions they cannot verify.

## Operation diagnostics

Read `agent.operation` for the active or most recent operation. Subscribe to `operation` events for snapshots at phase transitions, cancellation, completion, and idle:

```typescript
agent.events.on('operation', snapshot => {
  // Forward to your application metrics sink. Do not block this synchronous listener.
  console.log(snapshot.id, snapshot.status, snapshot.phase, snapshot.timings);
});
```

Snapshots include an operation ID, method kind, status (`running`, `draining`, or `finished`), outcome, elapsed time, and the last registered action's name, index, and dispatch state. They exclude prompts, URLs, page text, raw errors, and full action payloads. Click metadata is limited to the fields described in [Click feedback](/core-concepts/browser-interaction#click-feedback). Use static, nonsensitive custom action names. Existing logging, memory, and action/thought events retain their original payloads; this is not a global redaction setting.

| Last action state | Meaning |
| --- | --- |
| `pending` | The action was validated, but its resolver has not been called. |
| `started` | The resolver was called and has not settled. Side effects might already have happened. |
| `completed` | The resolver returned. This does not verify the application's business outcome. |
| `failed` | The resolver threw. Side effects might still have happened. |

Errors from accepted operations carry an `operation` snapshot when the error object is extensible. Built-in errors expose this field in their types. The original error identity and type are preserved. Frozen or custom errors may not accept metadata; use the getter or event in that case. `AgentBusyError.operation` identifies the conflicting active operation, when present.

A cancellation error retains the snapshot from cancellation, even if the worker later finishes. Later events and the getter show draining progress. `cancellationToDrainMs` measures time until the worker settles; `cancellationToIdleMs` also includes pending lifecycle cleanup. A finished snapshot can precede idle, so use `busy` and `whenIdle()` for reuse decisions. Keep listeners synchronous; catch failures in any asynchronous work you start from them. Synchronous diagnostic listener exceptions are logged without failing the operation.

### Provider attempts

Snapshots include `providerAttempts` after a model invocation settles. Each record comes from an actual BAML SDK call, including retries, rather than a planner step. The exported `ProviderAttemptDiagnostics` type contains:

| Field | Meaning |
| --- | --- |
| `operationId`, `attempt` | Operation correlation and a one-based attempt number within that operation. |
| `provider`, `model` | Configured provider and model, not values copied from response bodies. Model names are limited to 200 characters. |
| `startedAt`, `elapsedMs` | SDK start time in Unix milliseconds and duration, or `null` when duration is unavailable. |
| `httpStatus`, `requestId` | Response status and allowlisted request ID, or `null` when unavailable. |
| `outcome` | HTTP `succeeded` for 2xx, `failed` for other statuses, or `unknown` without a status. |

HTTP success does not establish successful parsing or task completion. An operation can fail or be cancelled even when an attempt reports HTTP success. Request IDs come only from `request-id` or `x-request-id` response headers and must contain at most 200 letters, digits, underscores, periods, colons, or hyphens. Other headers, URLs, prompts, response bodies, reasoning, and credentials are excluded. Use nonsensitive configured model names.

Magnitude retains the latest 100 attempts. `providerAttemptsTruncated` indicates that earlier records were dropped; attempt numbers continue increasing. Repeated snapshots contain the same records, so deduplicate by `(operationId, attempt)` when exporting events. Token usage remains separate, and an attempt can be recorded without usage.

The collector is not a live HTTP trace: attempts become available only after the SDK invocation settles. The installed SDK can report no response and a zero duration for a cancelled request that waited; Magnitude reports `null` duration, status, and request ID with `unknown` outcome in that case. The operation's model timing still measures the wait. Magnitude does not infer a provider timeout or rate limit from the application's cancellation or deadline. After cancellation, read later events or `agent.operation` after drainage; the error's earlier snapshot does not gain new records.

### Latency measurements

`timings` contains counts and total milliseconds for context construction, observations, model calls, action resolvers, screenshots, stability waits, cooldowns, retry waits, pauses, and cursor movement. A snapshot's phase is the most recently started active span, or `preparing` when none is active.

Totals are inclusive: action time can contain cursor and stability time, and observations can contain screenshot time. Concurrent spans also overlap. Do not sum these totals to calculate wall-clock duration; use `elapsedMs`. Native provider retries are included in model time; the separate retry category measures Magnitude's own retry sleeps. Durations use a monotonic clock. `startedAt` is Unix time in milliseconds for correlation.

Aggregate final snapshots by operation ID in your application to compare latency distributions. Magnitude retains only the current or most recent operation, not a persistent history.

To remove the cursor's 300 ms animation delay while keeping its visual position:

```typescript
const agent = await startBrowserAgent({
  // ...your model and browser settings
  visuals: { animateCursor: false },
});
```

`showCursor: false` disables the cursor drawing and its delay. Both cursor visibility and animation default to `true`. These options do not shorten browser stability waits.

## Typed outcomes

Import these errors from `@ddwang/magnitude-core`:

| Error | Meaning |
| --- | --- |
| `OperationCancelledError` | The caller cancelled, or `stop()` cancelled the operation. `cause` contains the supplied reason. |
| `OperationDeadlineError` | The operation reached its `deadline`. |
| `AgentBusyError` | Another operation is active or draining, or a lifecycle transition is pending. |
| `ActionLimitError` | The existing action budget was exhausted. |
| `BrowserBlockedError` | Browser recovery stopped execution. Inspect `block.reason`, `block.evidence`, and optional `block.retryAt`. |

If a site's `Retry-After` requires waiting beyond the operation deadline, Magnitude returns `BrowserBlockedError` with the original `retryAt`. It does not shorten the cooldown and retry early. An ordinary wait that reaches the deadline returns `OperationDeadlineError`.

## Custom actions and connectors

Action resolvers receive `signal` and `deadline` alongside `input`, `agent`, and `memory`. Connector `beforeAction`, `onTaskStart`, `collectObservations`, and `getInstructions` hooks receive the same controls as an optional final argument.

Forward the signal to cancellable APIs, check it before side effects after asynchronous preparation, and await all work you start:

```typescript
import { createAction } from '@ddwang/magnitude-core';

const action = createAction({
  name: 'fetch-record',
  resolver: async ({ signal }) => {
    const response = await fetch('https://example.com/record', { signal });
    const record = await response.text();
    signal?.throwIfAborted();
    return record;
  },
});
```

Magnitude cannot cancel arbitrary detached promises, undo a submission already sent, or control direct calls through `agent.page`, `agent.context`, or an external desktop interface. Built-in input cleanup may release a pressed mouse button or modifier after cancellation. A click or navigation already sent to Playwright may finish while the agent drains.

Applications must verify consequential outcomes before retrying. Login verification, 2FA, persisted sessions, and unknown-outcome reporting remain application responsibilities. Cancellation preserves memory already recorded; choose explicitly whether to reuse it on a later call. No memory migration is required.
