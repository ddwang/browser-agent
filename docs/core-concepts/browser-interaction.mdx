## Taking Action

Use **act()** to tell the agent what to do:

Instructions provided to act can be high-level tasks:
```ts
await agent.act('log in to the app');
```

or low level actions:
```ts
await agent.act('click the submit button');
```

Think of it like you're telling a coworker to do something. Breaking it up into tiny steps is unnecessary, but you want to be specific enough to make the objective clear.

### Chaining Acts

Combine multiple **act** calls to accomplish complex sequences of interactions:
```ts
await agent.act('go to tasks page');
await agent.act('assign all pending tasks to Bob');
await agent.act('move all pending tasks to "In Progress"');
```

You can also chain multiple steps together in the same act call for convenience:
```ts
await agent.act([
    'go to tasks page',
    'assign all pending tasks to Bob',
    'move all pending tasks to "In Progress"'
]);
```

### Providing Data

You can provide arbitrary data fields that the agent will use where appropriate during its actions:
```ts
await agent.act('create a new task', {
    data: {
        title: 'important task',
        description: 'some description'
    }
});
```

### Custom Prompting

Provide custom system prompt instructions as needed:
```ts
await agent.act('create a new task', {
    prompt: 'tasks should be written in spanish'
});
```

## Navigating Directly

While the agent is capable of navigating to URLs on its own, you may sometimes want to navigate to a specific URL directly.

To do this, use `nav`:
```ts
await agent.nav('https://google.com');
```

## Agent Capabilities

### What can agent do in act?

The agent is capable of **mouse**, **keyboard**, and **browser**-specific actions, including but not limited to:
- Clicking with the mouse
- Dragging with the mouse
- Typing long blocks of content
- Pressing specific keystrokes
- Switching tabs
- Navigating to URLs

### What is the agent aware of?

The agent knows about and sees:
- The current screenshot plus some past screenshots
- History of its own actions from the same `act()`
- All currently open tabs
- Which tab is active
- Browser download start, completion, and failure evidence for the current operation

## Click feedback

The next planner observation includes `browser-click` with the latest submitted click as `lastClick`, or `null` before a click in the current operation. The same record appears in operation diagnostics as `lastClick`; its exported type is `BrowserClickDiagnostics`.

The record contains the operation ID, action index, button, click count, executed viewport coordinates (`x`, `y`), and screenshot and viewport dimensions. Coordinates use CSS pixels after Magnitude's existing virtual-screen transformation. Screenshot dimensions refer to the last planner screenshot captured in that operation, including virtual-screen resizing. They are `null` when no screenshot has been captured in the operation, such as a direct `exec` call.

Immediately before submitting the mouse command, Magnitude inspects the hit element. `hit` contains an allowlisted standard tag and explicit ARIA role; it does not compute an accessibility role. Unknown or custom names become `null`. Inspection follows up to 16 open shadow roots. A frame target, unavailable document, or failed inspection returns unknown evidence. It does not traverse iframe documents or expose text, selectors, arbitrary attributes, values, or URLs. Custom controls and unknown targets still receive the original click.

Hit evidence is not proof that the intended control was activated. The page can change between inspection and dispatch. Magnitude does not retarget clicks, enforce a tag or role, or finish a task based on a hit. The planner uses the next screenshot and feedback to choose its next action. Cancellation during inspection prevents dispatch; cancellation after command submission cannot undo the click.

Only the latest click observation appears in normal planner context. A new operation replaces it with `null`, even with reused memory. The full memory audit can retain earlier observations. Click evidence does not reset no-progress counters; only the existing page and download progress signals do. No new browser listeners or recovery counters are added.

## Download evidence

Magnitude observes downloads on existing pages and new tabs before dispatching browser actions. The planner receives a `browser-downloads` observation containing an `operationId`, a `downloads` array, and a `truncated` flag. Each download has an opaque `id`, the initiating `actionIndex` where known, and one status:

| Status | Meaning |
| --- | --- |
| `started` | Chromium emitted a download event. The transfer is still pending. |
| `completed` | Playwright's `Download.failure()` resolved to `null`, confirming that the browser finished the transfer. |
| `failed` | The browser reported a failed transfer, or its terminal state could not be read. This is never treated as completion. |

These records contain no filenames, filesystem paths, URLs, error text, or downloaded contents. They do not save files or introduce a download manager. Completion confirms a transfer, not its contents or your application's business outcome. The planner decides whether the evidence satisfies the task; Magnitude does not automatically finish an operation when a download completes.

Magnitude retains at most 20 download records and completion observers per operation. Additional downloads set `truncated: true`. Only the latest download observation appears in the normal planner context. The existing full memory audit can still contain earlier snapshots. A new task replaces the evidence with an empty observation, including when you reuse memory. Completed, cancelled, and earlier task scopes cannot add evidence to the active task.

### Browser integration contract

Use a Playwright-compatible context with `acceptDownloads: true` and keep it open until the browser reports completion. With `acceptDownloads: false`, the local Chromium regression produces `failed`, not `completed`. Remote browser services must forward page and download events and support `Download.failure()`; a missing event provides no evidence of success or failure.

Keep the context exclusive to the agent during an operation. Magnitude attributes a download event to the last dispatched built-in browser action on that page, or the captured opener action for a popup. Playwright does not expose causal action IDs. Downloads triggered by unrelated automation, background timers, or external user input during a later action cannot always be distinguished. Downloads without a known initiating operation are omitted. Direct calls through `agent.page`, caller-defined actions, and downloads started before the connector attaches are outside this attribution contract.

Download events do not bypass screenshot collection. In local Chromium testing, an empty popup that immediately redirected to an attachment stalled screenshot capture after the download completed. A popup with a rendered document and a download link passed. Keep an operation deadline for browser observation stalls; this change does not replace the screenshot lifecycle.

Cancellation prevents late download completion from changing the operation's evidence or outcome. It does not undo the initiating click or cancel an already-started browser transfer. A pending transfer can continue after `whenIdle()`; use a fresh context if your application requires all browser-side activity to stop before reuse. Magnitude removes its download listeners when pages close or the connector stops.

## Attempts without progress

Enable the existing opt-in guard with `recovery: { noProgress: true }`. `repeatedActionLimit` defaults to `6` and must be an integer of at least `3`:

```ts
const agent = await startBrowserAgent({
    // ...your model and browser settings
    recovery: { noProgress: true, repeatedActionLimit: 6 },
});
```

The guard stops the next mutating browser action after either:

- Six attempts on an unchanged state, regardless of click variant or coordinate jitter.
- Twelve attempts through previously observed states without new evidence. This extra allowance permits familiar return paths after visiting a new record.

For another `repeatedActionLimit`, these bounds are the configured value and twice that value. New page evidence or a tracked download lifecycle transition resets both counters. Meaningful page evidence includes canonical URL, rendered document text, visible scroll offsets, and active form-control values. Magnitude's visual overlays, screenshot pixel changes, mouse coordinates, reasoning, and notebook writes do not establish progress. Text beyond the first 20,000 characters participates, so pagination on long pages remains observable within the collection limits below.

Fingerprinting runs in the browser with fixed limits of 10,000 visited DOM nodes and 262,144 processed characters. It returns a digest, not full page text. Barrier evidence is limited to 32 headings of 500 characters each. If a fingerprint is incomplete, Magnitude clears the current no-progress sequence rather than treating partial evidence as an unchanged page. Use an explicit `deadline` and finite `maxActions` to bound these operations; neither has a default limit. These caps bound the collector's own work, not Chromium's internal layout or screenshot time.

An unavailable fingerprint does not reset attempts against an explicitly detected authentication or subscription barrier. Those attempts reset when the barrier changes or two known fingerprints show a changed page. After three attempts against the same barrier, the next mutating action throws `BrowserBlockedError` with the barrier's reason.

Setting `recovery: false` skips recovery collection. With no-progress detection disabled, recovery still collects bounded barrier, scroll, and active-control evidence but skips general document text.

The guard remembers up to 4,096 state hashes per task without eviction; a long cycle cannot become new evidence by outgrowing a rolling window. At capacity, it conservatively treats additional page states as known. Task start resets this history. This remains a heuristic: canvas-only changes, iframe content, or repeated values can require disabling the guard or choosing a larger attempt allowance. Changing page text such as a clock can also appear to be progress.

On reaching a bound, the next mutating action throws `BrowserBlockedError` with `block.reason === 'no_progress'`. Observation collection, hover inspection, notebook actions, caller-defined actions, and task completion remain available. A `wait` does not consume or reset the no-progress allowance; fresh evidence observed after the wait can reset it. Pending downloads do not grant unlimited click attempts. Use `maxActions` and an operation `deadline` to bound planning and waits; there is no new global timeout. Rate-limit cooldowns retain their separate wait budget and typed outcome. See [Cancellation and deadlines](/advanced/cancellation).
